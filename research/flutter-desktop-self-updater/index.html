Self-Updating Flutter Desktop Apps via GitHub Releases

How the sarvdharm charity app checks GitHub Releases for new builds and updates itself — the pattern for distributing and auto-updating a Flutter Desktop Windows/Linux app without the Play Store or an enterprise MDM.

Mobile Flutter apps use the Play Store or App Store for distribution and updates. Desktop Flutter apps don’t have that infrastructure unless you build it yourself.

The sarvdharm charity registration app (a Flutter Windows/Linux desktop app for ticket issuance and disbursement management) ships via GitHub Releases and includes a self-updater: on launch, it checks the GitHub Releases API for a newer version and prompts the user to update.

The release pipeline

GitHub Actions builds the app on push to main:

- uses: subosito/flutter-action@v2
  with:
    flutter-version: '3.x'
- run: flutter build windows --release
- run: iscc installer.iss   # Inno Setup compiles the .exe installer
- uses: softprops/action-gh-release@v1
  with:
    files: |
      build/windows/x64/runner/Release/sarvdharm-installer.exe
      build/windows/x64/runner/Release/sarvdharm.zip

The release artifact is a signed Inno Setup installer (for first install) plus a zip (for self-update, which doesn’t need to run a full installer).

The self-updater check

The installer and the zip come out of the same build for different jobs: the signed installer is how a machine gets the app the first time, the zip is how an already-installed copy replaces itself without running an installer again.

On app startup, the app polls the GitHub Releases API:

final response = await http.get(
  Uri.parse('https://api.github.com/repos/haloyte/sarvdharm/releases/latest'),
);
final data = jsonDecode(response.body);
final latestVersion = data['tag_name'];  // e.g., "v1.3.0"

if (Version.parse(latestVersion) > currentVersion) {
  // Find the zip asset URL in the release
  final asset = (data['assets'] as List)
      .firstWhere((a) => a['name'].endsWith('.zip'));
  final downloadUrl = asset['browser_download_url'];
  // Prompt user and download
}

On Windows, the update flow downloads the zip, extracts to a temp directory, and uses a small launcher script that replaces the running executable on the next startup (since Windows won’t let you overwrite a running .exe).

Why Inno Setup for distribution

Inno Setup produces a .exe installer that handles:

  • Creating the application directory
  • Registering an uninstall entry in Windows Add/Remove Programs
  • Creating Start Menu shortcuts
  • Writing to the registry if needed

For an organization distributing to non-technical staff, an installer is more approachable than “extract this zip somewhere.” The self-updater zip is simpler because after first install, the paths are known and no registry work is needed.

The GitHub Releases approach vs. alternatives

For a small charity organization:

  • No app store overhead. Doesn’t require a Google Play Developer account ($25) or Microsoft Store submission.
  • No MDM. No need for Intune or similar enterprise software distribution infrastructure.
  • Versioned artifacts. GitHub Releases keeps a full release history; you can roll back by distributing an older release URL.

The tradeoff is no forced update. A user can stay on an old version indefinitely — the self-updater prompts, but doesn’t force. For internal tools at a single organization (where you control who has the app), this is usually acceptable.

For apps distributed to untrusted networks or requiring strict version enforcement, you’d add a minimum version check at the API layer and reject requests from clients below the floor version.

The Drift + PDF generation pattern alongside this

The app also demonstrates the full local-first Flutter Desktop stack:

  • Drift (SQLite ORM) for offline-first ticket and disbursement storage — no network dependency for core operations
  • PDF generation via the pdf package for printable ticket receipts
  • Local window management — native window sizing/placement APIs available in Flutter Desktop but not in mobile

This combination (local SQLite + printable receipts + self-updater) covers the practical requirements for a standalone charity registration kiosk running on a Windows PC without continuous internet.
