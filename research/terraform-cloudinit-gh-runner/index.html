Bootstrapping a GitHub Actions Self-Hosted Runner with Terraform + cloud-init

How the Haloyte infrastructure setup provisions a DigitalOcean server and automatically registers a GitHub Actions self-hosted runner on first boot — no manual SSH step, no post-provision configuration script, just cloud-init calling the GitHub API.

Adding a GitHub Actions self-hosted runner typically means: spin up a server, SSH in, download the runner package, run the configure script, start the service. The haloyte/infrastructure repo automates this entirely — the runner registers itself on first boot, with no manual intervention after terraform apply.

The Terraform layer

resource "digitalocean_droplet" "app_server" {
  image    = "ubuntu-22-04-x64"
  name     = "haloyte-prod"
  region   = "blr1"
  size     = "s-2vcpu-4gb"
  user_data = templatefile("${path.module}/cloud-init.yaml", {
    github_token = var.github_registration_token
    github_repo  = var.github_repo
  })
}

resource "cloudflare_record" "app" {
  zone_id = var.cloudflare_zone_id
  name    = "app"
  value   = digitalocean_droplet.app_server.ipv4_address
  type    = "A"
  proxied = true
}

Terraform provisions the droplet and DNS record together. The user_data field passes the cloud-init YAML as the first-boot script. Secrets (DigitalOcean API key, Cloudflare token, GitHub registration token) are Terraform variables — environment-specific .tfvars files are gitignored, not hardcoded.

The cloud-init bootstrap

cloud-init runs once on first boot. The bootstrap script:

#cloud-config
packages:
  - nginx
  - nodejs
  - npm
  - podman

runcmd:
  # Create a non-root user for the runner
  - useradd -m -s /bin/bash runner

  # Configure firewall
  - ufw allow 22/tcp
  - ufw allow 80/tcp
  - ufw allow 443/tcp
  - ufw enable

  # Get a runner registration token from GitHub API
  - |
    TOKEN=$(curl -s -X POST \
      -H "Authorization: token ${github_token}" \
      -H "Accept: application/vnd.github.v3+json" \
      "https://api.github.com/repos/${github_repo}/actions/runners/registration-token" \
      | jq -r '.token')

  # Download and configure the runner
  - mkdir -p /home/runner/actions-runner
  - curl -sL https://github.com/actions/runner/releases/download/v2.311.0/actions-runner-linux-x64-2.311.0.tar.gz | tar -xz -C /home/runner/actions-runner
  - |
    sudo -u runner /home/runner/actions-runner/config.sh \
      --url "https://github.com/${github_repo}" \
      --token "$TOKEN" \
      --unattended \
      --name "haloyte-prod"

  # Install and start the runner as a systemd service
  - /home/runner/actions-runner/svc.sh install runner
  - /home/runner/actions-runner/svc.sh start

The critical part is the GitHub API call: registration tokens are short-lived (one hour) and can’t be pre-generated into the Terraform config. cloud-init gets a fresh token at boot time, then uses it immediately to register.

Why cloud-init over a post-provision script

Alternative 1: Terraform null_resource + SSH. You could use a Terraform null_resource with a remote-exec provisioner to SSH in and run the setup after the droplet is ready. This requires SSH key management in Terraform state and has a race condition (waiting for SSH to be available after boot).

Alternative 2: Ansible playbook. More powerful, but adds another tool and a separate execution step after terraform apply.

cloud-init advantage: Runs inside the boot process — no separate tooling, no race condition on SSH availability, no state beyond what the droplet itself stores. The server is fully operational (Nginx serving, runner registered) by the time terraform apply completes.

The tf.sh wrapper + pre-commit hook

The repo includes a tf.sh wrapper script that:

  • Validates Terraform config before plan/apply
  • Checks for non-ASCII characters in .tf files (a Unicode trap that can silently corrupt Terraform configs when copied from certain editors)

The pre-commit hook runs this check automatically, catching the Unicode issue before it causes a confusing terraform plan error.

Podman instead of Docker

The bootstrap installs Podman rather than Docker. Podman is daemonless and rootless by default — containers can run as the runner user without requiring root or a docker socket. This matters for GitHub Actions: a runner that can run Docker requires either root or membership in the docker group, which gives broad system access. Podman avoids this.
