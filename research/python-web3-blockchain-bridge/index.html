Calling Solidity Contracts from a Python Web App via Web3.py

Architecture of a Flask + Web3.py bridge that records charity donations and payouts on Ethereum — two contracts (donation ledger + payout disbursement), how the Python backend calls on-chain functions after Razorpay confirms payment, and why server-side signing carries different risk than browser wallet approaches.

Most blockchain application tutorials use JavaScript + ethers.js or MetaMask to call contracts from the browser. But there are cases where you want the contract call to happen server-side: when you need to guarantee it happens as part of a larger transaction (payment confirmed → record on chain), when the user shouldn’t need a wallet, or when you’re handling funds that the user doesn’t directly control.

The Blockchain-Based NGO Donation Tracking project implements this: a Flask web app where Razorpay handles the fiat payment, and after Razorpay confirms, a blockchain.py bridge module records the donation on Ethereum Sepolia testnet.

The two-contract structure

Charity.sol       — records donations (who donated, how much, to which NGO)
NgoPayout.sol     — records disbursements from NGO to beneficiaries

Keeping them separate enforces a clean logical boundary: incoming funds and outgoing funds are tracked in different contracts. This makes on-chain transparency auditable — a donor can verify their donation was recorded, and the NGO can separately verify each disbursement was authorized.

The blockchain.py bridge

from web3 import Web3

w3 = Web3(Web3.HTTPProvider(os.environ["RPC_URL"]))
private_key = os.environ["SIGNER_PRIVATE_KEY"]
account = w3.eth.account.from_key(private_key)

charity_contract = w3.eth.contract(
    address=os.environ["CHARITY_CONTRACT_ADDRESS"],
    abi=CHARITY_ABI
)

def record_donation(donor_address: str, ngo_id: int, amount_wei: int) -> str:
    tx = charity_contract.functions.recordDonation(
        donor_address, ngo_id, amount_wei
    ).build_transaction({
        "from": account.address,
        "nonce": w3.eth.get_transaction_count(account.address),
        "gas": 200000,
        "gasPrice": w3.eth.gas_price,
    })
    signed = w3.eth.account.sign_transaction(tx, private_key)
    tx_hash = w3.eth.send_raw_transaction(signed.rawTransaction)
    return tx_hash.hex()

The bridge builds, signs, and broadcasts the transaction from the server. The signer account is the backend’s own Ethereum account (funded with Sepolia ETH for gas), not the donor’s wallet.

The payment → chain recording flow

Donor completes Razorpay checkout
    → Razorpay sends payment.captured webhook to Flask
        → Flask verifies webhook signature (HMAC-SHA256 against Razorpay secret)
            → blockchain.py.record_donation(donor_email_hash, ngo_id, amount_wei)
                → Sepolia testnet records the transaction
                    → Flask stores tx_hash in MySQL for future lookup

The donation amount in the contract is the fiat amount converted to wei for display, not an actual ETH transfer — the funds stay in Razorpay’s settlement. The on-chain record is an immutable audit trail, not a custody transfer.

Server-side signing vs. browser wallet

The server-side approach has different tradeoffs than MetaMask/browser wallet:

Advantages:

  • No wallet required for donors. Lower friction — a donor with no crypto experience can donate without installing anything.
  • The recording is guaranteed to happen as part of the backend flow, not at the donor’s discretion.
  • One signing key handles all transactions; no need to coordinate with user wallets.

Risks:

  • The private key is a server-side secret. If the server is compromised, the signer account is compromised. With a browser wallet, the private key never leaves the user’s device.
  • Nonce management becomes the backend’s problem. If two concurrent requests both call w3.eth.get_transaction_count() before either broadcasts, both get the same nonce and one will be rejected.
  • Gas cost is the backend’s expense, not the user’s. For a donation platform this may be intentional (transparent UX), but it means the backend needs a gas budget.

Nonce management under concurrency

The nonce issue is the most common failure mode for server-side signers under concurrent load. The fix is to manage nonces explicitly rather than reading from chain each time:

with nonce_lock:
    nonce = w3.eth.get_transaction_count(account.address)
    tx = contract.functions.recordDonation(...).build_transaction({
        "nonce": nonce,
        ...
    })
    signed = w3.eth.account.sign_transaction(tx, private_key)
    w3.eth.send_raw_transaction(signed.rawTransaction)

A lock (threading.Lock, or a distributed lock via Redis for multi-process deployments) ensures nonces are assigned sequentially. The blockchain.py bridge in the NGO project doesn’t implement this — a concurrency failure would require a manual nonce reset.
