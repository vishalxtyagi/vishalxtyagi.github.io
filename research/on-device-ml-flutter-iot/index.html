On-Device ML Inference in Flutter for IoT Sensor Predictions

Architecture of a smart irrigation system where sensor data flows from ESP8266 firmware through Firebase to a Flutter app that runs an on-device SVM model to predict irrigation need — no prediction API call, inference runs locally on the phone.

Most mobile ML demos use TFLite — but TFLite is designed for neural networks. For tabular predictions (classification/regression on structured sensor data), sklearn-family models are more appropriate, and bundling them in Flutter is less commonly documented.

The Smart Irrigation IoT project does this: an SVM trained in Python is exported as JSON and loaded in Flutter via the sklite package to predict whether to irrigate, based on live sensor readings and weather data.

The data flow

Firebase is the only meeting point: the phone and the board never talk directly, they both publish and subscribe to the same keys. Relay commands pay a round trip for it (typically 100–500ms), which irrigation can afford and a fast actuator could not.

The decision loop never touches a server after initial model load. The phone does inference locally using the Firebase-streamed sensor values as features.

Why SVM instead of a neural network

For this problem domain:

  • Low feature count. 3–5 features (temperature, humidity, soil moisture, precipitation forecast). SVMs generalize well here; neural networks would overfit on this size dataset without regularization.
  • No inference latency requirement. Irrigation decisions don’t need sub-10ms response. But they do need to work offline (poor connectivity in rural IoT settings). On-device inference with a bundled model survives spotty internet.
  • Training interpretability. The project was academic/demonstrative — an SVM decision boundary can be visualized and explained. A trained neural network is harder to justify in a college project presentation.

Bundling the model for Flutter

The Python training workflow:

from sklearn import svm
from sklite import Serializer

clf = svm.SVC(probability=True)
clf.fit(X_train, y_train)

Serializer.toFile(clf, 'assets/svm.json')

The sklite library serializes the SVM’s support vectors, coefficients, and hyperplane parameters to JSON — a format Flutter can read. The Flutter side:

String modelJson = await rootBundle.loadString('assets/svm.json');
var model = SVC.fromJson(jsonDecode(modelJson));
List<double> features = [temperature, humidity, soilMoisture, ...weatherFeatures];
int prediction = model.predict(features);

The model runs synchronously on the UI thread (negligible compute for a small SVM). No Isolate needed. Compare with TFLite, where even small models warrant running inference off the main thread.

What breaks at scale

Single-user Firebase structure. The schema stores one set of readings at a fixed path (/sensors/current). Multiple NodeMCUs writing to the same path would overwrite each other. A multi-device deployment needs keyed paths (/sensors/{device_id}/current).

Static model. The SVM is trained once and bundled. If sensor readings drift over time (sensor aging, different soil types), the model’s training distribution diverges from production. A real deployment would need periodic retraining and model update delivery — either via dynamic_cached_fonts-style URL-based model updates or a CI-triggered app release.

Hardcoded credentials. The ESP8266 firmware has Firebase API keys embedded in source. For deployment, these should live in a secrets.h file excluded from version control, or use the ESP8266’s LittleFS to store credentials in the onboard flash separately from firmware.
