Semantic Similarity for Subjective Exam Grading

Using transformer embeddings and cosine similarity to grade short-answer responses — the pipeline from scanned PDF to score, where this approach beats keyword matching, and where the hardcoded threshold makes it fragile.

Grading short-answer responses is hard to automate because students phrase correct answers differently. Keyword matching fails: “the mitochondria generates ATP” and “ATP is produced in the mitochondria” are equivalent, but share no exact n-gram. Semantic similarity via sentence embeddings is a better fit: encode both into a shared vector space, measure cosine distance.

This is the approach EvalSheet uses.

The pipeline

Student PDF upload
    → pdf2image converts pages to JPEG frames
        → Google Cloud Vision API extracts text (OCR)
            → HuggingFace sentence-transformers encode student text + answer key
                → cosine_similarity(student_embedding, key_embedding)
                    → score = similarity × question_marks (if above threshold)

Three external dependencies do the heavy lifting: Vision API for OCR (handles handwriting better than Tesseract for cursive), sentence-transformers for semantic encoding, and scikit-learn’s cosine_similarity for the comparison.

Why embeddings over keyword matching

A keyword matcher would look for terms from the answer key in the student response. Problems:

  1. Synonyms. “Generate” vs. “produce” vs. “create.” A keyword matcher penalizes these; an embedding model that was trained on natural language doesn’t.
  2. Paraphrase. “The process occurs in the presence of oxygen” vs. “This is an aerobic process.” Same meaning, zero keyword overlap.
  3. Ordering. Keyword matchers can be fooled by a response that includes all the right terms in the wrong conceptual structure. Embeddings capture sentence-level semantics, not just token presence.

The tradeoff is interpretability: with a keyword matcher you can explain exactly why a response scored low. With cosine similarity, you can show the score but not which part of the student answer differed semantically from the key.

The threshold problem

The scoring logic is:

if similarity_score >= THRESHOLD:
    score = similarity_score * question_marks
else:
    score = 0

THRESHOLD is a hardcoded constant. This is the biggest practical weakness. The right threshold depends on:

  • Subject domain. Exact-science answers (chemistry equations, definitions) cluster tightly in embedding space — a high threshold (0.85+) is appropriate. Humanities or essay answers have more legitimate variation — you’d want a lower threshold (0.65–0.75) or a sliding scale rather than binary accept/reject.
  • Answer key length. Very short keys (“Mitosis”) yield noisy similarities because there’s little signal to embed. Longer, more complete reference answers produce more discriminative embeddings.
  • Model choice. all-MiniLM-L6-v2 (fast, small) and all-mpnet-base-v2 (slower, higher quality) have different absolute cosine score distributions. A threshold calibrated for one model will misfire on another.

A production deployment would need threshold calibration against a labeled dataset of human-graded responses — at minimum, running the model on past graded exams and finding the threshold that maximizes agreement with human scores.

OCR as the weak link

Google Cloud Vision handles printed text well and has reasonable accuracy on neat handwriting. But for cursive, smudged, or low-contrast scan quality — common in physical exam settings — OCR errors propagate downstream. A student who wrote a correct answer that OCR misread as garbled text will have their embedding computed on the garbled text, producing a low similarity even if they answered correctly.

The pipeline has no OCR confidence gate. Adding one (reject low-confidence OCR output and flag for manual review rather than auto-scoring) would significantly reduce false negatives.

What this demonstrates that keyword search doesn’t

Running the pipeline end-to-end requires understanding:

  • PDF ingestion (Poppler bindings, cross-platform path issues — EvalSheet has a PR specifically for Windows Poppler path resolution)
  • Cloud OCR API integration (credential management, response parsing)
  • Transformer inference without fine-tuning (zero-shot reuse of a pretrained model)
  • Cosine similarity as a distance metric in embedding space
  • Role-based web app plumbing (Flask, SQLAlchemy, file upload handling)

It’s a real ML pipeline — not a single model call, but a composition of document processing, OCR, NLP inference, and threshold-based scoring, all wired into a user-facing web application.
