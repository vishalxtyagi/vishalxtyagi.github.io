Product Analytics & Event Tracking Architecture

A deep architectural look at the custom ProductAnalytics tracking facade built for Runo, introducing windowed event deduplication, platform-aware config target separation, and Hive-based CRM event accumulation.

Every user click, pipeline update, and calling event needs to map to a standardized event shape. When tracking is scattered directly inside features, dashboards break, duplicate identifications occur, and non-production testing clutters real metrics.

This case study covers the design decisions, code boundaries, and tradeoffs behind building a unified tracking facade.

Problem Statement

Before this implementation, analytics calls were made directly using the vendor SDK, scattered across feature views, billing flows, and CRM actions. This created three major pain points:

  1. Dirty Data in Production: Sandbox runs and testing profiles regularly leaked events into production dashboards because environment checks were performed inline or omitted.
  2. Duplicate Identifications: Re-authenticating or toggling state triggered redundant .identify() calls, skewing unique user retention charts.
  3. Network Congestion: Telephony and CRM activity updates fired an HTTP request per individual user action, resulting in API rate limits and battery drain on mobile.

Constraints

  • The CRM serves both mobile clients (with offline modes) and web clients (Flutter Web) using a single codebase.
  • User and account properties (company size, role, billing tier) must stay synchronized with every event payload without requiring the developer to attach them manually at each call site.
  • Logging and debugging should occur transparently in sandbox environments without loading the full Amplitude SDK.

Alternatives Considered

Direct SDK Wrappers

Integrating the vendor’s SDK directly with a global helper function.

  • Why Rejected: Failed to isolate the codebase from the vendor interface. Changing analytics providers later would require modifying hundreds of scattered call sites.

Middleware/Third-Party Analytics Platform (e.g. Segment)

  • Why Rejected: Adding another abstraction layer increased bundle size and runtime cost unnecessarily when only one downstream destination (Amplitude) was required.

Decision: A Platform-Aware Custom Facade

We designed a unified ProductAnalytics class implementing an abstract AnalyticsProvider interface. This facade serves as the single gatekeeper for tracking, identity management, and event batching.

flowchart TD
    App[Feature Actions] -->|AppEvent| Facade[ProductAnalytics Facade]
    Facade --> Env{Environment?}
    
    Env -->|Sandbox/Dev| DevLogs[Log to Console / Escape]
    Env -->|Production| Filter[Deduplication Filter]
    
    Filter -->|Duplicate| Drop[Drop Event]
    Filter -->|Unique| Route{Event Type?}
    
    Route -->|Standard Event| Amp[AmplitudeProvider]
    Route -->|CRM Summary| Accumulator[CrmActivityAccumulator]
    
    Accumulator -->|Batch & Save| HiveStore[(Hive Local Storage)]
    HiveStore -->|Flush on Lifecycle| Amp
    Amp -->|HTTP POST| AmplitudeCloud[Amplitude Endpoints]

Implementation Details

1. Identity & Trait Standardisation

Instead of using ad-hoc property maps, the system enforces a strict type definition (ProductAnalyticsUserTraits) covering:

  • Enrollment timestamps
  • Organization ID and team capacity
  • Current billing tier

The facade intercepts all session startups, caches these properties, and automatically appends them to all subsequent events.

2. Time-Windowed Deduplication

A time-windowed deduplication filter keeps track of the last processed event names and timestamps. If a duplicate event with identical properties is fired within a configured window, the filter intercepts and drops it.

3. CRM Activity Accumulation

To solve the network congestion issue, we introduced CrmActivityAccumulator backed by Hive local storage. Key actions are buffered and summarized locally:

    participant Facade as ProductAnalytics

    Amp->>Hive: Clear batch cache

Key Decisions & Tradeoffs

[!NOTE] Environment boundary separation is enforced strictly: sandbox hosts skip SDK initialization entirely, reducing bundle initialization latency by ~140ms in development environments.

  • Asynchronous local write vs. Immediate sync: We traded real-time accuracy for network efficiency. Activity updates are batched, meaning events may be delayed by up to a session boundary, but network overhead dropped significantly.
  • Strict schemas vs. Free-form maps: Schema-less maps are rejected. Adding new tracking categories requires defining them in the AppEvent catalog, keeping dashboard schemas pristine.

Retrospective & Lessons Learned

  • Flush Timing: Early versions flushed batches on a standard 30-second timer. Testing showed events fired right before an app was swiped away were lost. The architecture was updated to hook into the native lifecycle observer, executing a flush operation the moment the app enters the background state.
  • Analytics Ownership boundaries: Structuring the analytics facade made it clear that telemetry is a shared product-and-engineering asset. Defining standard event schemas in the codebase serves as code-based documentation that engineers and product managers can read side-by-side.
