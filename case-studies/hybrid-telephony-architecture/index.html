Case study

SIM and cloud calling in one account

SIM tracking and cloud telephony existed separately for years; this made them one account-level capability

Runo's app had SIM call tracking and Airtel IQ cloud calling, but an account could only use one. This is how they became one account-level capability.

2 min read

Challenge
An account could use SIM call tracking or Airtel IQ cloud calling, never both. Switching meant reconfiguring the account.
Approach
One SIM / Cloud / Hybrid setting, an orchestrator that keeps both calling drivers live in one session, and a per-call choice of path.
Impact
Accounts run both calling paths at once with no reconfiguration, and every call records the path it used, so reports agree.

Before

SIM tracking or cloud (Airtel IQ), never both, per account

→

After

Both simultaneously, one account, one session

Attribution
callMedium on activity and reports

Situation

Runo’s app already shipped two calling paths before this work started: native SIM-based call tracking, and cloud virtual numbers over Airtel IQ. The limitation wasn’t that these didn’t exist; it’s that an account could only run one of them:

Moving an account between modes, or adding a virtual number, meant reconfiguring the account, not a setting an operator could flip. Reporting also forked into parallel mode branches that didn’t agree on which medium a given call actually used.

Constraint

  • Both calling paths must be usable on the same account at once, not just switchable
  • Same behavior required on Android, iOS, and admin web
  • Availability gated by role permissions and virtual-number allocations
  • Workflow layer must not assume low-level transport details of each driver

Decision

Replace the account-level either/or flag with runtime state that lets both drivers be active on one session. A session-preserving orchestrator manages both channel drivers at once instead of gating one behind the other.

Primitives

  • Enum model: SIM / Cloud / Hybrid, replacing the account-level either/or flag
  • Driver orchestrator: keeps both channel drivers live on one session instead of one gating the other
  • CallMediumSelector: default or per-interaction override once both paths are available
  • callMedium attribution: events, activity logs, exports, dashboards tagged with which path a call actually used

Tradeoff

Rejected alternative: keep the account-level either/or model and just make switching between them faster/lighter-weight. Simpler state model, but it doesn’t fix the actual limitation: accounts still couldn’t use both capabilities they already had.

The enum/orchestrator approach takes on real in-session concurrent-state handling complexity (two drivers genuinely live at once now, not one swapped for another), plus a one-time cleanup of legacy accounts sitting in inconsistent either/or states. Both real costs, taken deliberately in exchange for actually removing the exclusivity rather than making it more convenient to switch.

Evidence

  • Accounts run SIM tracking and cloud telephony simultaneously, no account-level reconfiguration required
  • Reporting uses one attribution field per call instead of parallel mode branches that could disagree
  • Adding a virtual number or changing allocation no longer requires taking the other calling path away

No measured drop in support tickets or reconfiguration requests is claimed here; that would need a baseline that wasn’t tracked before this work. The verifiable change is architectural: the exclusivity is gone, not just easier to work around.
