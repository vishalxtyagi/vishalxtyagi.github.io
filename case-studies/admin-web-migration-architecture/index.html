Admin Web Platform Migration & Architecture

A deep-dive case study on the architectural restructuring of Runo's internal administration platform, detailing the creation of a frontend sheet validation engine, reusable multi-step upload controllers, and dirty-check state wrappers.

Every operational team relies on the internal administrative control panel. The admin platform manages customer lists, sets allocation rules, handles key pairs, and configures lead sources. If these workflows are buggy or sluggish, support tickets accumulate rapidly.

This case study covers the architecture of migrating scattered admin workflows into a cohesive, modular Flutter Web design system.

Problem Statement

The legacy admin system had each page implementing its own data validation, loading states, and networking. This generated three main engineering concerns:

  1. Redundant Code: CSV/Excel parsing, loading animations, and column mapping logic were duplicated across upload, deletion, and settings pages.
  2. Edits Lost by Accidental Navigation: Users filling out complex integration mappings lost in-progress work if they clicked outside dialog boundaries or hit the browser back button.
  3. High Fetch Latency: Sub-pages repeatedly queried the main user and team lists instead of utilizing a unified state cache, resulting in network lag.

Constraints

  • Single Codebase: Must compile for mobile platforms and Flutter Web without separate codebase forks.
  • Large Datasets: Upload templates must support validation of files with up to 10,000 rows without locking the main browser UI thread.
  • Backwards Compatibility: The column validation rules must remain synchronized with existing CRM database column schemas.

Alternatives Considered

Direct Server-Side Validation

Pushing raw files directly to the server and letting backend scripts return line-by-line errors.

  • Why Rejected: Poor feedback loop for operators. Validating on the server forced users to wait for network roundtrips, uploading large files only to find a formatting typo on row 900.

Completely Stateless Pages

Using simple stateless UI widgets and stateless controllers.

  • Why Rejected: Stateful forms (like Excel columns mapper selectors) contain complex temporary UI states. Forcing them to be stateless required propagating massive boilerplate parameter listings.

Architecture: Reusable Admin Components

We restructured the layout to separate UI mapping pages from sheet validation utilities. The SheetValidationUtil runs on the client, checking headers against CRM definitions before sending payloads.

flowchart TD
    File[CSV / Excel Template] --> Pick[TemplateUploadWeb UI]
    Pick --> Validate{SheetValidationUtil}
    
    Validate -->|Invalid Columns| Error[Display Row/Col Error inline]
    Validate -->|Valid Columns| Stepper[CustomStepper Controller]
    
    Stepper --> Preview[Mapping Preview Grid]
    Preview --> Confirm[Safe Commit Dialog]
    
    Confirm -->|Is Dirty?| Warning[Show wrapDialogWithDirtyCheck Dialog]
    Confirm -->|Save| Commit[API Client Request]

1. Sheet Validation Utility (SheetValidationUtil)

Client-side column validation was abstracted out into a standalone Dart utility:

  • Detects the existence of required fields like mobile_number and customer_name.
  • Normalizes variations in column naming (e.g. Mobile vs phone_number) against a static dictionary.
  • Reports structural formatting errors (exceeding row size limits, corrupted character encoding) before starting the upload session.

2. Multi-Step Stepper Controller (CustomStepper)

We built a reusable multi-step upload controller:

  • Step 1: Pick File: Validates structure and schema.
  • Step 2: Column Mapping: Maps user-defined headers to target CRM fields.
  • Step 3: Preview: Shows a grid preview of processed records.
  • Step 4: Execute: Performs bulk API operation with progress feedback.

3. Navigation Dirty Checks (wrapDialogWithDirtyCheck)

To protect against lost state, we wrapped the dialogs in custom controllers that track form changes:

// Generic state checking signature
bool safeGetIsDirty(StatefulForm form) {
  return form.currentPayload != form.originalPayload;
}

The navigator hooks into browser pop events. If safeGetIsDirty returns true, it shows a confirmation dialog before allowing the user to navigate away.

Key Decisions & Tradeoffs

[!TIP] Grouping code structure horizontally by feature directory (placing models, services, and view layers in a single folder) reduced the friction of building new admin workflows. Developers can add a new upload tool by editing a single feature namespace.

  • Frontend validation thread lock: Running file parsers on the web thread can cause brief drops in frame rate during parsing of large files. We accepted this tradeoff over the complexity of spawning separate web workers because of the browser compatibility overhead.

Retrospective & Lessons Learned

  • Cached Configuration Data: Reusing shared process configurations instead of re-fetching lists on page load reduced database query volumes by approximately 30%.
  • Dirty Checks Ubiquity: Applying state validation guards globally resolved the issue of lost inputs, proving that standardizing user safety behaviors should be designed at the platform layer.
