Runo Product Analytics & Amplitude Instrumentation

Worked on a product analytics layer at Runo — Amplitude provider abstraction, event taxonomy, user/company traits, deduplication, and platform-aware tracking across auth, billing, CRM, and call workflows.

This case study describes patterns and architecture inferred from commit history at Runo, a private codebase. Business outcomes (retention lift, funnel conversion changes) are intentionally omitted because they aren’t independently verifiable from available source material. Claims here are phrased as “worked on” / “contributed to” rather than “led,” per the evidence policy in this site’s README.

Every click and action in Runo needs to get counted correctly on a dashboard somewhere — someone, somewhere, is looking at a funnel chart and trusting the numbers in it. This work made sure that counting actually happens once and accurately, instead of getting duplicated, missed, or quietly mixed up between the web app and the mobile app.

Problem & Context

Before this work, “tracking” mostly meant: whoever built a feature bolted on an analytics call wherever it felt right. No shared identity for events, no agreed-on way to attach user or company context, no deduplication, no awareness of which platform (web vs. mobile) or environment (sandbox vs. production) the event even came from. It worked, in the sense that events showed up somewhere — it just wasn’t something you could trust a dashboard on.

Solution & Architecture

The fix was a single front door: a ProductAnalytics abstraction sitting on top of an AmplitudeProvider. The rest of the app calls one tracking surface and never has to know or care which analytics backend — or which environment — is actually on the other end of it.

flowchart LR
  A[App event call sites] --> B[ProductAnalytics facade]
  B --> C{Environment check}
  C -->|production, logged in| D[AmplitudeProvider]
  C -->|sandbox / not logged in| E[No-op / logged skip]
  D --> F[Amplitude]
  B --> G[CrmActivityAccumulator]
  G --> H[(Hive local storage)]

The pieces that made this actually hold up:

  • Provider abstraction — AmplitudeProvider implements an AnalyticsProvider interface, so initialization, identify, track, and flush logic all live behind one contract instead of being copy-pasted at each call site.
  • User/company traits — structured ProductAnalyticsUserTraits instead of loose, ad hoc property maps, covering signup date, team size, and account-level metadata consistently.
  • Deduplication — a time-windowed dedupe check, tuned over several iterations, so the same user action fired from two overlapping code paths doesn’t get counted twice.
  • Platform targeting — AnalyticsTargetPlatform detection, so web and mobile can behave differently where it actually matters (page-view autocapture, for instance, is off on web and selectively on for mobile).
  • CRM activity accumulation — CrmActivityAccumulator, backed by Hive (local on-device storage), quietly batches up CRM activity before reporting it, instead of firing one event for every tiny action a user takes.

Key Decisions & Tradeoffs

[!NOTE] Sandbox/non-production hosts intentionally skip Amplitude initialization, with an explicit forceSandbox escape hatch for testing — trading a small amount of debug friction for protecting production analytics data quality.

  • Chose to centralize identification logic in ProductAnalyticsUtils rather than scattering identify() calls near each login/signup site, after observing duplicate identification attempts.
  • Increased the event deduplication window after follow-up commits suggested the original window was too short for catching the events it was meant to catch.
  • Renamed report_events to activity_events and moved internal_analytics to product_analytics — a deliberate internal-naming cleanup that traded short-term churn for clearer long-term boundaries between “raw analytics events” and “CRM activity summaries.”

Implementation Details

Instrumentation was added across login/signup, payment success, billing flows, attendance, rechurn, templates, allocation rules, CRM fields, search execution, detail views, and filters — using the same AppEvent shape so new events follow an existing pattern rather than inventing local conventions each time.

Lessons Learned

  • Analytics infrastructure is the kind of work that’s easy to keep putting off, precisely because it touches everything and nothing about it looks broken until you go looking. The deduplication and skip-logging additions only became necessary after the first version shipped and the data started looking noisier than it should.
  • Flush behavior had to become asynchronous and tied to actual app lifecycle changes — not just a timer — because a timer doesn’t know the app is about to close, and events fired right before backgrounding were quietly getting dropped.

[!WARNING] Earlier versions of this system had an auto-identification path that was later removed — a reminder that “automatically identify when possible” can quietly create duplicate or premature identify calls if not scoped carefully to login state.
