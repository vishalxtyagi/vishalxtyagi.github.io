Runo Admin Web Migration

Contributed to migrating Runo's admin web surface to Flutter Web, building reusable components for bulk upload/deletion, integration dialogs, and sheet validation.

This is the internal control panel Runo’s own team uses day to day — uploading customer lists in bulk, deleting records, managing API keys, wiring up third-party tools. Nobody outside the company sees this screen, but the whole sales team leans on it constantly, so when it’s slow or buggy, everyone feels it at once.

Problem & Context

The admin tasks — bulk upload, deletion, downloads, API keys, integrations — lived across older pages that had each grown their own version of the same plumbing. Process data, templates, column mappings, user lists, loading states, validation logic: reinvented, slightly differently, on nearly every page that needed it. Fixing a bug in one upload flow told you nothing about whether the same bug existed in the other three.

Solution & Architecture

Instead of patching each page separately, the work built one shared set of admin-web building blocks, so every workflow could compose the same pieces rather than growing its own slightly-different copy.

Notable components:

  • CustomStepper / TemplateUploadWeb — a shared multi-step upload flow used by both bulk upload and deletion pages.
  • SheetValidationUtil — centralizes mandatory-field and max-field-size validation against DefaultCrmColumns/StandardFieldName, so upload validation rules live in one place rather than per-page.
  • AdminWebDropdown / AdminWebDropdownMultiple — reusable searchable dropdowns replacing one-off CustomSelector implementations.
  • Cached process data — bulk upload pages were refactored to reuse cached process/user/reportee lists rather than re-fetching on every step, reducing loading-state churn.

Key Decisions & Tradeoffs

[!NOTE] Several admin-web pages were rebuilt as StatefulWidgets with explicit loading/error states rather than relying on simpler stateless patterns — a deliberate tradeoff favoring predictable UX over minimal boilerplate, given how much state these flows juggle (selected columns, template options, dirty-check confirmations).

  • Introduced a “dirty check” pattern (wrapDialogWithDirtyCheck, safeGetIsDirty) across admin dialogs to prevent silent loss of in-progress edits — a direct response to early versions where users could navigate away mid-edit without warning.
  • Standardized on typed integration classes instead of a single IntegrationEnum, trading some verbosity for stronger type safety across Facebook/Meta, WABA, HubSpot, Zoho, and Salesforce integration dialogs.

Implementation Details

The migration moved admin_web models, services, and components into a features directory structure, and later to a feature-folder codebase reorganization — routine but necessary work to keep a growing admin surface navigable as more integrations and workflows were added.

Lessons Learned

The reusable upload/validation pieces paid for themselves quickly: once SheetValidationUtil and CommonUploadStep existed, a new allocation-specific or customer-specific upload variant meant extending shared logic, not writing a fourth copy of it. That’s the kind of investment that’s easy to skip when a deadline is close, but it keeps paying rent on every admin workflow built after it.

The dirty-check pattern ended up traveling further than expected. It started as a fix for one specific complaint — users losing in-progress edits by accidentally navigating away — but once wrapDialogWithDirtyCheck existed as a reusable wrapper, it just became the default for any new admin dialog holding meaningful state, not only the upload flows it was built for. The lesson: a fix scoped to one bug report is often worth generalizing right away, if the underlying problem (unsaved state, an accidental click away) shows up across a whole surface rather than one page.
